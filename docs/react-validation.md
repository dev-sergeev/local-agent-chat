# Проверка упрощённого ReAct-бэкэнда

Проверено 12 сентября 2026 года на Linux, с реальной моделью DeepSeek V4 Flash 0731 через OpenRouter. Браузерные сценарии выполнялись через публичный маршрут JupyterHub `/user/admin/vscode/proxy/<port>/`, с запущенным в терминале Chainlit и сохранением его логов.

## Изменение архитектуры

Один `create_agent` и четыре инструмента чтения (`ls`, `read_file`, `glob`, `grep`) заменили Deep Agents, режимы доступа к хосту, подагентов, загрузку project skills и общую долговременную память. Между запросами SQLite хранит сообщения и сводку; откат восстанавливает принадлежащий приложению снимок, без зависимости от внутренних узлов LangGraph.

Объём `app.py` и Python-модулей `local_agent_chat/` сократился примерно на четверть. Архитектура описана в [ADR 0011](adr/0011-use-one-sandboxed-react-loop.md).

## Автоматические проверки

`pytest -q`: **161 passed, 31 subtests passed**. Единственное предупреждение — устаревшая форма конфигурации Pydantic в зависимости `traceloop`, без ошибок приложения.

Проверены:

- 100 запросов через настоящий граф `create_agent` с управляемой моделью, правки позиций 1, 2, 25, 26, 50, 75, 99, 100 и последующий перезапуск.
- Многократная суммаризация, перенос важного факта, восстановление точного контекста до правки и отсутствие будущего продолжения.
- Суммаризация большого импортированного контекста порциями без потери начала входных данных; целостность пар tool-call/result.
- Ошибка, отмена, пустая и обрезанная сводка, пустой ответ, превышение окна и ограничение бесконечного цикла инструментов.
- Запрет выхода за песочницу, обхода через symlink и чтения специальных файлов; ограничение вывода, чтение поздних страниц и поиск по большим файлам.
- Согласованность UI, файлов и SQLite при ошибках сохранения и редактировании; одинаковые временные метки сообщений.

`ruff check .`, `ruff format --check .`, `compileall`, `bash -n scripts/run.sh`, `git diff --check` прошли. Установка проекта в editable-режиме также прошла.

## Браузер и реальная модель

Достигнута глубина **100 запросов пользователя и 100 ответов**. После каждого завершённого запроса проверялись текст, порядок и идентификаторы текущих Turns, соответствие сообщений UI, отсутствие потерянных родителей шагов и пустота временных архивов восстановления. Для баз выполнялись `integrity_check` и `foreign_key_check`.

Для частого сжатия использовались уменьшенные бюджеты: окно 8000, порог 3000, сохранение последних 800, сводка 400 и ответ 500 токенов. Суммаризация прошла **пять раз**. После сотого запроса активный контекст содержал 43 сообщения и примерно 2888 токенов; UI сохранял все 100 пар. Модель вернула точный код `CANARY-REACT-7482`, заданный в первом запросе. Повторное открытие страницы сохранило ту же историю.

Отдельно проверена копия старого чата из 100 запросов: продолжение до 101, правки 50-го и 3-го запросов, повторное открытие. Поздний файл из 80-го запроса исчез после правки 50-го, файл из 20-го оставался; после правки 3-го оба отсутствовали.

После перезапуска сервиса выполнена правка 50-го запроса с остановкой после 10 порций потокового ответа. Все 100 исходных пар восстановились; хеш сериализованного контекста совпал с исходным. Дополнительных фрагментов ответа в SQLite не осталось. Повторное открытие страницы подтвердило результат. Для длинного потокового ответа использовался штатный лимит 2000 токенов.

Попытка заменить 50-й запрос текстом на 30 000 символов корректно отклонена по бюджету контекста. UI показал уведомление об ошибке, лог сервиса содержал причину, все 100 пар и точный прежний контекст сохранились.

Через нативный редактор проверены позиции **100, 99, 75, 50, 26, 25, 2, 1**, включая повторную правку последнего сообщения и продолжение после изменений. На границах суммаризации 25/26 сохранился первоначальный идентификатор. После правки 50-го сообщения использовался новый идентификатор; после возврата к более раннему запросу этот будущий факт исчезал. После изменения первого запроса прежние идентификаторы отсутствовали в активном контексте.

В основном UI загружен текстовый файл и реально вызваны все четыре инструмента. Содержимое возвращено корректно, сам файл не изменился. Попытка прочитать специально созданный контрольный файл вне песочницы вернула отказ; его содержимое не появилось в контексте. Проверено повторное открытие диалога.

## Найденные и исправленные причины сбоев

1. У reasoning-модели весь маленький бюджет суммаризации мог уйти на рассуждение: измерено 400 выходных токенов, все 400 — reasoning, без полезной сводки. В профиле добавлены отдельные `summary_options`; в примере OpenRouter reasoning для сводки выключен. Основной ответ сохраняет собственные настройки.
2. Служебные поля сообщений и перечисление повторяющихся обменов перегружали сводку. Суммаризатор получает полное содержимое разговора и данные инструментов без транспортных метаданных, с явным заданием краткости. Пустая или обрезанная сводка откатывает запрос, сохраняя прежнюю историю.
3. Сортировка UI по времени и UUID меняла порядок сообщений с одинаковой временной меткой. Добавлен постоянный `stepOrder`, используемый также при удалении продолжения и откате.
4. Stop и задача диалога одновременно записывали завершение отменённого ответа. Поздняя запись могла появиться уже после восстановления истории. Удалён второй путь записи; откат и его UI-записи принадлежат одной задаче. Повторный Stop не отменяет уже выполняющийся откат. Сбой воспроизведён через UI и отдельным тестом с управляемым порядком событий; оба сценария прошли после исправления.
5. Ошибка правки могла исчезнуть вместе с временными UI-шагами. После отката теперь отправляется отдельное уведомление, причина ошибки записывается в лог сервиса.
6. Модель иногда искала сообщённый пользователем факт в файлах вместо разговора. Системная инструкция явно разрешает обычное общение и использование фактов переписки без загрузки файлов. Повторная проверка первого сообщения и следующего запроса вернула исправленный идентификатор. Выбор отдельных безопасных вызовов инструментов остаётся за моделью.
7. Контекстный менеджер соединения `sqlite3` завершает транзакцию, но не закрывает соединение. До исправления 200 операций при отключённом GC оставляли 202 открытых дескриптора. Соединения хранилищ контекста, профилей, текущей истории и начальной миграции UI теперь явно закрываются; тот же прогон оставляет 0. Это проверяется отдельными тестами без зависимости от сборки мусора.

Артефакты, исходные проверки SQLite, скриншоты и логи находятся локально в `.local-agent-chat/backend-refactor/` и не включаются в Git. Перед обновлением основного экземпляра сохранена копия его данных в `main-before-migration/`.

Основной экземпляр обслуживает порт 8765 с `APP_DATA_DIR=.local-agent-chat/revision-validation/data` и публичным префиксом `/user/admin/vscode/proxy/8765`. Это тот же каталог данных, который использовал предыдущий запущенный экземпляр; `.env` с пользовательским значением `APP_DATA_DIR` не перенаправлялся.

После последнего обновления основного процесса через UI проверены восстановление чата, новый запрос, редактирование последнего запроса и перезагрузка страницы. Удалённый вариант отсутствует в активном контексте, целостность всех трёх баз подтверждена. Текущий лог процесса: `.local-agent-chat/backend-refactor/main-server-release.log`. Дополнительные тестовые экземпляры остановлены.

Суммаризация остаётся сжатием с потерями: проверка сохранения контрольного факта не доказывает сохранение любого произвольного факта. Бюджет токенов оценивается консервативно; его следует согласовать с окном выбранного провайдера. Полная текущая история UI хранится независимо от сводки.
